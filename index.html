같은 메시지가 여러 번 저장되지 않게

  1. 문제네트워크가 불안정하면 앱이 같은 메시지를 다시 보내고, 재전송이 동시에 도착하면 같은 메시지가 여러 번 저장될 수 있었습니다.
  2. 판단메시지 ID에 UNIQUE 제약을 걸되, 같은 트랜잭션 안에서 제약 위반을 잡으면 트랜잭션 전체가 롤백 대상이 되어 나머지 요청이 500 에러로 끝난다는 점을 고려했습니다.
  3. 구현저장만 REQUIRES_NEW로 별도 트랜잭션에 분리하고, 중복이면 새 트랜잭션에서 먼저 저장된 메시지를 찾아 그대로 돌려주게 했습니다.

결과같은 메시지 100건을 동시에 보내도 1건만 저장되고 에러는 0건입니다. UNIQUE가 없으면 100건이 모두 저장됐고, 같은 트랜잭션에서 처리하면 99건이 에러였습니다. 로컬 재현 실험 10회 모두 같은 결과였습니다.

  2. 판단한 연결에는 한 번에 하나만 쓰게 하고, 연결이 끊긴 사실은 AI 서버 요청까지 전달해야 한다고 판단했습니다.
  3. 구현쓰기와 종료를 하나의 락으로 묶고, 종료 신호가 오면 AI 서버의 스트림 구독을 바로 취소하게 했습니다.

  3. 구현결과를 반영할 때 작업 행에 락을 걸고 현재 상태를 확인하며, 처리 중 취소는 '취소 중' 상태로 따로 관리했습니다.

로그아웃이 반만 처리되지 않게

  2. 판단Refresh Token을 DB에 저장해, 서버가 토큰 상태를 직접 관리하기로 했습니다.
  3. 구현재발급할 때는 기존 토큰을 폐기하고 새 토큰을 발급하며, 로그아웃은 하나의 트랜잭션으로 묶었습니다.

테스트를 통과한 코드만 자동 배포

  2. 판단PR과 배포 두 단계 모두에서 테스트를 강제하고, 배포 성공은 서버가 실제로 응답하는지로 판단하기로 했습니다.
  3. 구현GitHub Actions로 PR마다 테스트와 빌드를 실행하고, develop에 합쳐지면 Docker 이미지를 커밋 해시로 태그해 EC2에 배포하도록 구성했습니다.

결과배포 후 60초 안에 헬스체크가 성공하지 않으면 파이프라인이 실패로 끝나 문제를 바로 알 수 있고, 이미지마다 붙은 커밋 해시로 어떤 코드가 배포됐는지 추적할 수 있습니다.

매주 변경된 코드를 AI로 한 번 더 점검

  2. 판단반복되는 점검은 AI에게 맡기고, 무엇을 고칠지는 사람이 판단하기로 했습니다.
  3. 구현GitHub Actions에 Claude Code를 연결해, 매주 월요일 지난 일주일 변경분만 리뷰하고 결과를 Discord로 받도록 구성했습니다. SQL 인젝션, 인증 누락, N+1 쿼리, 트랜잭션 범위, 테스트, 로깅 등 15개 기준을 프롬프트로 정의했습니다.

    UNIQUE 제약으로 중복 저장을 막고, REPEATABLE READ에서 다른 트랜잭션의 커밋이 보이지 않는 점을 고려해 설계합니다. 스키마 변경은 Flyway로 기존 데이터를 채워가며 단계적으로 반영합니다.

  • Spring Security · JWT

    인증과 인가를 나눠 리소스 소유권까지 확인하고, Refresh Token 로테이션과 WebSocket 연결 인증을 구현했습니다.

  • Redis

    대화 세션 상태를 저장하고, WATCH와 MULTI로 같은 초안이 두 번 등록되지 않게 막았습니다.

  • AI 활용

    Claude Code로 반복적인 코드 점검을 자동화하고, AI가 낸 결과는 코드와 맥락을 직접 확인한 뒤 반영합니다. 서비스에 붙인 AI의 응답도 그대로 믿지 않고 저장 전에 검증합니다.

  • 테스트

    동시 요청을 재현하는 테스트와 외부 서비스를 대체한 통합 테스트로, 예외 상황까지 코드로 검증합니다.
